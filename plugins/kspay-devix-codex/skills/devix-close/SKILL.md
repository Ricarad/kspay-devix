---
name: devix-close
description: Close a completed Devix change, cancel a discontinued requirement at any stage, or archive an ended change.
---

Read the target change's formal files and determine whether the user means successful completion, cancellation, or archiving. A bare request to close an unfinished change is ambiguous unless the conversation already explains that the requirement is being dropped. Resolve that ambiguity before mutating it. Use an explicit change id for a paused or historical change; never substitute the active change. `devix change list --include-archived` helps locate it.

- Successful completion: run `devix change validate --strict`. Confirm verification evidence, release SOP execution or an explicit no-impact waiver, resolved/deferred/waived decisions, monitoring and delayed cleanup. Advance one phase to closed only after the verification gate and release completion conditions are satisfied. Do not self-approve human gates. Write a concise resume summary; reusable knowledge must be independent of this change.
- Cancellation: when the user explicitly drops or discontinues the requirement, run `devix change cancel <id> --reason <user-stated reason> --reviewer <confirming user>`. It is allowed at any unfinished phase, including a pending revision. Do not pass completion gates or rewrite release/test results to make cancellation look successful. The CLI preserves the phase, records cancellation and stops unfinished task rows. Check the remaining prose/decisions for inconsistent promises and record outstanding release/rollback ownership in release.md when applicable. Preserve pending release work as pending; cancellation does not perform rollback or cleanup.
- Archiving: when requested, use `devix change archive <id> --reason <reason> --reviewer <confirming user>` after cancellation or normal completion. For cancellation plus archive, pass `--archive` to cancel. Files and branches remain in place; the archive record is separate from cancelled/done. Do not archive unless requested.

An explicit cancellation request already supplies authorization; ask only for missing reason/identity or an unresolved Git conflict. On WORKSPACE_CONFLICT, show the expected/actual branch, HEAD and dirty files. Never retry with `--adopt-current-branch` without confirmation. Active cancellation saves a local WIP through the existing pause rules; inactive cancellation uses existing snapshots and never touches another active checkout. Do not delete branches, reset, stash or push. Ended changes cannot be resumed through switch/revise; a new requirement needs a new change referencing the historical material.

After cancellation or archive, inspect `devix change status <id>` and `devix change validate <id> --strict`; report the outcome, saved snapshot, archive state and any remaining release actions. Do not treat pre-existing incomplete delivery gates as cancellation failures.
