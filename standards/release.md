# Release 文档与上线 SOP 规范

`release.md` 是单个 change 的发布事实源，记录远程配置、基础组件、环境差异、执行顺序、监控、回滚和上线后动作。测试用例与验收结论仍写入 `verification.md`，不能在两份文件中维护两套发布正文。

## 1. 按实际影响编写

- 每个 schema v2 change 固定包含 `release.md`，但正文只记录本需求真实存在的发布影响。
- 没有发布影响时，只保留“发布影响、判断依据、确认状态”三项精简结论。
- 有发布影响时才增加发布范围、环境差异、上线 SOP、监控、回滚和实际发布记录。
- Kconf/Kconfig、Redis、Task、RPC、MQ、数据库、权限、开关等组件只在实际涉及的时候出现。禁止保留“无”“不涉及”的组件标题、空表格或占位章节。
- 编码中新增或取消某类影响时，同步增加或删除对应内容，不能让旧方案继续留在文档中。

## 2. 有发布影响时的通用内容

根据本次事实组织文档，至少回答：

1. 发布哪些仓库、服务或制品，顺序和负责人是什么。
2. Staging、PRT、Prod 分别需要什么配置或操作，目标值是否不同。
3. 哪些动作必须在代码部署前完成，哪些在部署后或验证后执行。
4. 每个动作的前置依赖、执行状态、计划/实际时间和证据在哪里。
5. 如何验证配置生效，观察哪些日志、指标和告警，观察窗口多长。
6. 触发回滚的条件、代码和配置的回滚顺序、回滚后的验证方式。
7. 是否存在临时日志、延迟开关、数据清理或二次上线，以及负责人和截止时间。

环境和时机使用统一名称：

- 环境：`Staging / PRT / Prod`。
- 时机：`部署前 / 部署中 / 部署后 / 验证后`。
- 状态：`pending / ready / doing / done / blocked / cancelled`。

## 3. 组件专项信息

只选择实际涉及的类型：

- Kconf/Kconfig：namespace/key、变更字段、各环境当前值和目标值、生效方式、传播时间、默认值与回退值。
- Redis：集群或资源引用、key 前缀、TTL、容量、数据兼容、预热、清理和回滚方式。
- Task：调度平台、任务名、handler、cron、分片、并发、misfire、部署前禁用和部署后启用顺序。
- RPC：服务、方法、版本、超时、重试、路由、降级、白名单以及 provider/consumer 上线顺序。
- 其他组件：记录资源标识、环境差异、启停/生效顺序、验证和回滚所需的最小事实。

## 4. 编写与更新时机

- clarification：创建文件，判断 `release.impact`，不确定时保持 `pending`。
- design：根据真实代码链路识别组件和环境差异，形成初版 SOP 与回滚方案。
- implementation：配置字段、TTL、RPC 契约、任务启停、发布顺序、临时日志或回滚方案变化后立即更新。
- 进入 verification 前：补齐 Staging、PRT、Prod 的准备动作、负责人和回滚，交由用户或发布负责人确认 release_readiness gate。
- verification/实际发布：持续记录执行时间、状态、版本和证据，不把计划当成已完成。
- closed 前：完成监控观察、临时项清理和上线后动作；有发布影响时 `release.status` 必须为 `completed`。

## 5. 安全与证据

- 密钥、Token、密码、私钥和生产连接串不得写入 change，只记录安全平台引用、配置版本或可公开的校验信息。
- 当前值或回滚值含敏感信息时使用受控平台引用，不复制明文。
- “已完成”必须有可定位证据，例如配置版本、发布单、日志/监控链接、命令结果或人工确认记录。
- 同一事实发生变化时修改原条目并保留必要的实际执行记录，不并列保留互相冲突的方案。
