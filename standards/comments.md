# 注释规范

> 本文只提供业务仓库未明确规定时的缺省规则。若目标仓库或模块的 `AGENTS.md` 对注释语言、格式、JavaDoc/Docstring 等有要求，优先遵守仓库规则。

## 核心标准

注释解释代码本身无法表达的“为什么”：业务约束、反直觉行为、兼容原因、并发/时序保证、外部协议限制和重要取舍。能通过清晰命名表达的“做了什么”不写注释。

## 应该写

- 规则来源不明显，例如额度、时间窗口、状态转换限制。
- 实现看似可以简化，但受历史兼容或下游协议约束。
- 锁、事务、缓存、重试等存在必须保持的顺序。
- 临时兼容逻辑，并且能给出删除条件或跟踪项。
- 公共 API/SDK 按仓库既有规范说明契约、边界和异常。

示例：

```java
// 先持久化再释放 token 锁，避免查询方看到 generating=false 时数据仍不可见。
saveMaterials(materials);
releaseGenerateLock(token);
```

## 不应该写

```java
// 获取用户信息
User user = userService.getUser(userId);

// 遍历列表
for (Item item : items) {
    ...
}
```

禁止以下模式：

- 逐行翻译代码，或给每个简单步骤编号。
- “新增”“修改”“优化”“2026-xx-xx by 某人”等版本历史；历史属于 Git。
- “这里需要注意”“显而易见”等没有给出具体约束的空话。
- 注释掉的旧代码、调试代码和大段复制的需求原文。
- 对尚未验证的推断使用确定语气。
- 为了显得完整，机械给所有 private 方法、字段和简单 DTO 添加注释。

## 语言和风格

- 默认跟随所在仓库的主流语言；中文业务仓库可用简洁中文解释业务原因，协议名和代码符号保留原文。
- 一条注释只表达一个关键原因，紧贴所约束的代码。
- 注释随行为一起更新；无法确认仍然真实的注释应先验证，不能盲目保留。
