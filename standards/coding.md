# 代码生成规范

> 本文只提供业务仓库未明确规定时的缺省规则。目标仓库或更具体模块的 `AGENTS.md` 优先于本文。

## 1. 修改原则

- 先找到真实入口、调用链、数据模型、配置和测试，再开始设计改动。
- 优先沿用仓库已有分层、命名、异常、日志和依赖注入方式。
- 只抽象已经出现的稳定共性；不为假想复用提前增加接口、工厂或通用框架。
- 一个提交/任务围绕一个可描述的目的，避免顺手格式化或重构无关代码。
- 不吞异常，不使用无边界重试，不把业务失败伪装成成功返回。

## 2. 兼容与安全

- 接口、数据库、消息、缓存 key、配置和序列化模型变更必须逐项检查兼容性。
- 默认值必须保守；开关关闭时保持旧链路语义。
- 幂等、事务、并发、超时、降级和回滚在设计阶段说明，不能留到上线前补想法。
- 不在代码、日志、测试样例或文档中写入密钥、token 和真实敏感数据。

## 3. AI 生成约束

- 不生成不存在的类、接口、配置或命令并当作已验证事实。
- 参考实现只作为证据；复制前逐项说明相同点和差异点。
- 不留下“TODO: 后续完善”来掩盖当前验收范围；确需延期时进入 tasks/decisions。
- 不批量添加无信息量的 getter、步骤编号或“本次新增”注释；类头作者与创建日期仅按 [`comments.md`](./comments.md) 的固定格式生成。
- 交付前检查 diff，确认没有调试代码、无关格式变化和被注释掉的旧实现。

## 4. 提交控制

- 生码和验证完成后不得自动执行 `git commit` 或 `git push`。
- 先向用户汇报修改文件、验证结果、未验证项和风险；只有用户明确要求提交后，才能创建正式 commit。
- change 切换时为保存脏功能分支而创建的本地 `WIP(devix)` 快照属于现场恢复机制，不等同于生码完成后的正式提交，仍须严格遵守 Devix 的分支预检规则。

## 5. 命名

- 名称表达领域含义，不使用 `data/info/obj/temp/handle/doIt` 等无法区分职责的泛化词。
- 布尔值使用可判断真假的语义，如 `enabled`、`hasPermission`、`shouldRetry`。
- 同一概念在数据库、接口、模型、配置和文档中保持一致；显式协议例外需写入 decisions。

## 6. 异常日志

- 本规则适用于所有 SLF4J Logger 实例，不依赖对象名是 `log`、`logger` 或其他名称。
- 支付团队代码打印日志时禁止使用 `+` 拼接消息字符串。普通日志不携带异常时，按仓库惯例使用 SLF4J `{}` 占位符。
- 日志需要同时记录动态业务参数和异常堆栈时，不使用 SLF4J `{}` 占位符传递业务参数；先用 `String.format(...)` 生成完整消息，再把异常作为唯一的第二个参数传入：`log.error(String.format("operation failed, identifier=%s", identifier), e)`。
- 禁止 `log.error("operation failed, identifier={}", identifier, e)` 这类“SLF4J 占位参数 + 末尾异常”混合调用；必须让调用形式明确匹配 `error(String msg, Throwable t)`，避免异常被按普通参数处理而丢失堆栈。
- 消息不包含动态参数时直接使用 `log.error("operation failed", e)`，不为固定文本套 `String.format`。
- 异常日志仍需遵守敏感信息约束，不打印完整请求体、素材正文、token 或其他真实敏感数据。
